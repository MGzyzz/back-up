# Дизайн: веб-дашборд по бэкапам

**Дата:** 2026-09-04
**Статус:** утверждён, готов к планированию реализации
**Дополняет:** сервис отчётов в Google Sheets (задание №1). Не заменяет его.

## 1. Цель

Сегодня узнать судьбу бэкапов за день можно только из файла Google Sheets,
который создаётся раз в сутки. Нужен экран, где человек выбирает дату
(по умолчанию — сегодня) и сразу видит, **какие бэкапы в каких средах прошли,
а какие нет**, по живым данным Telegram, а не по вчерашнему файлу.

Фронт и бэк поднимаются в Docker, одним `docker compose up`.

## 2. Что уже есть и переиспользуется

Существующий код закрывает почти всю содержательную часть:

- `internal/telegram` — `FetchDay(ctx, day) []parser.RawMessage`
- `internal/parser` — текст сообщения → `Backup`
- `internal/report` — `Aggregate([]Backup) []Job`

`report.Job` — это готовая строка дашборда: `Environment`, `Label`, `Name`,
`OK`, `Start`, `End`, `Node`, `Nodes`. Новой бизнес-логики задача не требует.

Два свойства `Aggregate`, на которые опирается дизайн:

1. **Правило статуса.** Задача успешна, если хотя бы одна нода отчиталась
   `SUCCESS`: бэкапы стоят на кластере, команда выполняется на одной ноде,
   остальные шлют «command was not executed». Правило живёт в `Aggregate`
   и **не должно повторяться на фронте**.
2. **Порядок.** Задачи отсортированы по (провал раньше успеха, среда, имя).
   Фронт группирует по средам в порядке первого появления — и среда с провалом
   всплывает наверх сама, без сортировки в UI.

## 3. Принятые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Раскладка репозитория | Монорепо: `back_end/`, `front_end/`, `docker/` | Симметричные имена, один `docker compose up` для проверяющего |
| Судьба Google Sheets | Остаётся нетронутой | Задание №1 в критериях приёмки заказчика |
| Форма бэка | Два бинаря: `cmd/report`, `cmd/api-server` | Образ сервера не содержит ни кода Google API, ни OAuth-токена |
| Жизнь соединения | Соединение на запрос + кэш `access_hash` и результата | Обход диалогов дороже выгрузки истории и повторяется зря; кэш снимает риск `FLOOD_WAIT` |
| HTTP-слой | Gin | Требуется для изучения |
| Фронт | Vite + React + TypeScript + Tailwind v4 | Привычный стек; TS окупается на nullable-полях модели |
| CORS | Не нужен вовсе | nginx проксирует `/api` — браузер видит один origin |

## 5. Изменения в существующем коде

Ровно две точки, обе вынуждены задачей, обе поведения не меняют.

### 5.1 `config.RequireGoogle()`

Сейчас `prepare()` требует `GOOGLE_OAUTH_CLIENT`, `google.folder_id`,
`google.token_path` и `retention_days` безусловно — сервер без них не стартует.
Эти четыре проверки переезжают в экспортированный метод `RequireGoogle()`,
который `cmd/report` вызывает первой строкой после `LoadConfig`. Для `report`
ничего не меняется: те же ошибки, те же тексты, та же агрегация через
`errors.Join`.

### 5.2 Кэш `access_hash` в `telegram.Client`

`resolvePeer` обходит все диалоги аккаунта постранично по обеим папкам, чтобы
добыть `access_hash` канала. Обход остаётся (он защищает от «канал уехал
в архив»), но найденный `access_hash` запоминается в поле клиента, и повторный
`FetchDay` идёт сразу к истории. Прозрачно для обоих бинарей.

### 5.3 Новый блок конфига

```yaml
server:
  addr: ":8080"
  cache_ttl_today: 60s
  cache_ttl_past: 1h
```

Блок **необязательный**, у всех полей есть значения по умолчанию в коде.
Сделать его обязательным нельзя: это сломало бы `cmd/report` на существующем
`config.yaml`.

## 6. Контракт API

```
GET /api/report?date=YYYY-MM-DD     date необязателен, по умолчанию сегодня
GET /api/health
```

Успешный ответ:

```json
{
  "date": "2026-09-04",
  "fetched_at": "2026-09-04T10:41:02+05:00",
  "cached": true,
  "stats": { "messages": 30, "backups": 15, "skipped": 15 },
  "jobs": [
    {
      "environment": "KT",
      "label": "MINIO_VK_CLOUD_BACKUP",
      "name": "MinIO VK Cloud",
      "ok": false,
      "start": null,
      "end": null,
      "duration_seconds": null,
      "node": "",
      "nodes": ["kt-backup01"]
    }
  ]
}
```

DTO живёт в `internal/api`, а не в `report`, по двум причинам: нулевой
`time.Time` сериализовался бы как `0001-01-01T00:00:00Z` вместо честного
`null`, и json-теги на доменном типе впустили бы формат транспорта в домен.

`stats` считает сообщения, а не задачи: `messages` — сколько сообщений отдал
канал за сутки, `backups` — сколько из них разобралось в `Backup`, `skipped` —
сколько отсеялось как не про бэкап (`ErrNotBackupMessage`: чужие уведомления
в том же канале, отчёты о восстановлении). Длина `jobs` меньше `backups`:
задачи сворачиваются по нодам.

`nodes` — **всегда массив**, никогда `null`: иначе `.map` на фронте падает.
`start`, `end`, `duration_seconds` — `null` у задач без времён (статус `ERROR`).

Ошибки — всегда `{"error": "..."}`:

| Случай | Код |
|---|---|
| `date` не парсится, либо дата в будущем | 400 |
| `telegram.ErrNoSession` | 503, текст про необходимость `-login` |
| `FLOOD_WAIT` от Telegram | 503 + заголовок `Retry-After` |
| остальное | 502 |

При протухшей сессии сервер **не падает**, а отвечает 503: контейнер остаётся
живым, причина видна в интерфейсе.

## 7. Кэш и параллелизм

Один мьютекс вокруг похода в Telegram плюс повторная проверка кэша после
захвата. Два одновременных запроса за одну дату дают один поход — второй
читает готовое. Это заодно защищает `data/session.json` от одновременной
записи двумя MTProto-соединениями.

TTL: сегодняшний день — 60 с (данные ещё меняются), прошедшие — час (сутки
закрыты). Флага принудительного сброса нет: короткого TTL достаточно, а
байпас кэша вернул бы риск `FLOOD_WAIT`. Чтобы «обновить» не выглядело
сломанным при попадании в кэш, ответ несёт `cached` и `fetched_at`, и UI
показывает время получения данных.

## 8. Сервер

`gin.New()` (не `Default()`) с собственным middleware поверх `slog` — логи
сервера должны выглядеть как логи остального проекта. Graceful shutdown через
`&http.Server{Handler: engine}` и `Shutdown(ctx)`: `engine.Run()` его не умеет.

### 8.1 Конкурентность

Горутины в проекте есть, но пишем мы одну. Запросы раздаёт по горутинам сам
`net/http`, соединение внутри себя ведёт `gotd/td`; наша — только та, что ждёт
сигнал и зовёт `Shutdown`.

Главное следствие конкурентного сервера — не горутины, а общее состояние:
кэш и `telegram.Client` читаются из нескольких горутин сразу, и без мьютекса
из §7 два параллельных запроса откроют два MTProto-соединения к одному
`data/session.json`. Мьютекс здесь про целостность файла сессии, а не про
скорость.

Сознательно не делаем:

- **Параллельный разбор сообщений.** Их за сутки десятки, `parser.Parse` —
  разбор строки в map. Горутина обойдётся дороже самой работы.
- **Пул MTProto-соединений.** Аккаунт и сессия одни, параллелить нечего,
  попытка упрётся в `FLOOD_WAIT`.
- **Фоновый прогрев кэша по тикеру.** Заставил бы сервис ходить в Telegram,
  когда дашборд никто не открывал, — расход лимитов аккаунта без адресата.
- **Воркер с каналом вместо соединения на запрос.** Отвергнут при выборе
  модели жизни соединения (§3).

Показательно, что в дизайне v1 задания №1 было две горутины — сборщик
и публикатор, — и обе исчезли, когда спайк показал, что юзер-аккаунт читает
историю. Здесь тот же принцип.

## 9. Фронт

### 9.1 Раскладка

```
front_end/src/
├── types.ts              ReportResponse, Job — зеркало DTO бэка
├── api/client.ts         fetchReport(date), разбор {error} в типизированную ошибку
├── lib/group.ts          группировка Job[] по средам + счётчики (чистая функция)
├── lib/format.ts         время и длительность, null → «—»
├── components/
│   ├── DateBar.tsx       <input type="date"> + «обновить» + «данные на 10:41»
│   ├── EnvSection.tsx    заголовок среды, счётчик 5/7
│   ├── JobRow.tsx
│   └── StatusBadge.tsx
└── App.tsx
```

Дата — нативный `<input type="date">`, без библиотеки датапикера. Ни роутера,
ни state-менеджера, ни UI-кита.

### 9.2 Группировка

`lib/group.ts` собирает `Job[]` в `Map<environment, Job[]>` **в порядке первого
появления**. Собирать нужно по всему списку, а не непрерывными кусками: сервер
кладёт все провалы в начало, поэтому задачи одной среды приходят двумя
участками. Порядок сред и порядок строк внутри среды наследуются от сервера —
своей сортировки на фронте нет.

### 9.3 Состояние

```ts
type State =
  | { kind: 'loading' }
  | { kind: 'refreshing'; data: ReportResponse }
  | { kind: 'ok'; data: ReportResponse }
  | { kind: 'error'; message: string; retryAfter?: number }
```

`refreshing` отделён от `loading` намеренно: при смене даты экран пустеет и
показывает скелет, при нажатии «обновить» данные остаются на месте, а индикатор
идёт сверху. Иначе каждое обновление мигает пустотой.

### 9.4 Состояния экрана

| Состояние | Что показываем |
|---|---|
| Первая загрузка | скелет секций |
| Обновление | данные + полоска сверху |
| Успех | секции по средам |
| Пусто | «за 4 сентября в канале нет сообщений о бэкапах» |
| 503, нет сессии | «сервер не может войти в Telegram: нужен повторный `-login`» |
| Прочая ошибка | текст из `{"error"}` + кнопка «повторить» |

Пустой день и сломанная сессия — **разные экраны**. Свалить их в одно «нет
данных» значит спрятать протухшую сессию, а её чинят руками, и молча она
не всплывёт.

### 9.5 Адрес

Выбранная дата уезжает в query фронта (`/?date=2026-09-04`) через
`history.replaceState`, без роутера. Открытая на другом устройстве ссылка
показывает тот же день.

## 10. Docker

### 10.1 Часовые пояса

Конфиг зовёт `time.LoadLocation`. В `scratch` и `distroless/static` базы
часовых поясов нет, и это падает **в рантайме**, а не на сборке. Базовый образ
рантайма — `alpine` с `ca-certificates` (TLS к Telegram) и `tzdata`.
Альтернатива `import _ "time/tzdata"` отвергнута: пакет виден в Dockerfile,
импорт — спрятан.

### 10.2 Образы

- `back_end/Dockerfile` — multistage: `golang:1.27-alpine` собирает
  **оба** бинаря с `-trimpath`; рантайм `alpine`, непривилегированный
  пользователь, `WORKDIR /app`, бинари в `/app/api-server` и `/app/report`,
  `CMD` — `api-server`.
- `front_end/Dockerfile` — `node:22-alpine`, `npm ci && npm run build`,
  затем `nginx:alpine` со статикой и встроенным `nginx.conf`.
- `front_end/nginx.conf` — `/api/` проксируется на `back_end:8080`, остальное
  падает в `index.html`.

### 10.3 Compose

```yaml
services:
  back_end:
    build: ./back_end
    env_file: [ ./back_end/.env ]
    volumes:
      - ./back_end/data:/app/data
      - ./back_end/config.yaml:/app/config.yaml:ro
    healthcheck: [ CMD, wget, -qO-, http://localhost:8080/api/health ]
  front_end:
    build: ./front_end
    ports: [ "8080:80" ]
    depends_on: { back_end: { condition: service_healthy } }
```

Короткая запись `build: ./back_end` и `build: ./front_end` задаёт отдельный
контекст каждого сервиса и берёт `Dockerfile` из его корня. Бэкенд и фронтенд
можно собирать независимо, без путей за пределы контекста.

**`WORKDIR /app`, и монтирование идёт туда же.** Флаг `-config` по умолчанию
равен `config.yaml`, а `telegram.session_path` и `google.token_path` в конфиге
относительные (`data/...`). Если разложить их по `/etc` и `/data`, один и тот же
`config.yaml` перестанет работать на хосте и в контейнере одновременно.
С `WORKDIR /app` пути совпадают, и ни флагов, ни второго конфига не нужно.

Наружу публикуется только фронт; бэк живёт во внутренней сети compose.
**`secrets/` бэку не монтируется вовсе** — `client_secret.json` нужен только
`report`, а сервер про Google не знает.

### 10.4 Секреты

Compose не понимает `export` в `env_file`, а `env.sh` состоит из них. Чтобы
не держать два списка переменных, зависимость переворачивается: появляется
`back_end/.env` (и `.env.example` в репозитории), а `env.sh` схлопывается в
`set -a; . ./.env; set +a`. Источник правды один.

### 10.5 Логин

```sh
docker compose run --rm -it back_end /app/api-server -login
```

`api-server -login` входит только в Telegram: Google дашборду не нужен. Один раз,
интерактивно; пишет `session.json` в смонтированный том. На
Linux-хосте файл окажется под UID контейнерного пользователя — в README будет
строчка про это.

## 11. Тестирование

`internal/api` через `httptest` и фейковый `Source` (интерфейс уже описан
в `app`):

- форма JSON: времена приходят `null`, а не `0001-01-01`; `nodes` — массив
- 400 на кривую дату и на дату в будущем
- 503 при `telegram.ErrNoSession`
- кэш: два запроса подряд — один поход в источник
- истёкший TTL — поход повторяется
- десять горутин на одну дату — по-прежнему один поход в источник

`internal/config` — тесты обновляются под `RequireGoogle` и новый блок `server`.

Фронт: vitest на `lib/group.ts` и `lib/format.ts` — среда с провалом наверху,
задача без времён, пустой список. Компонентных и e2e-тестов нет: дизайном
не занимаемся.

Тест кэша `access_hash` в `telegram` не пишется — MTProto не подделывается
через `httptest`. Это тот же осознанный размен, что описан в §11 дизайна
задания №1.

## 12. Порядок работ

1. Переезд Go в `back_end/`, создание `docker/`; `go test ./...` зелёный
2. `config`: `RequireGoogle()` и блок `server` с дефолтами
3. `internal/api`: DTO, кэш, хендлеры — по TDD
4. `cmd/api-server`: Gin, slog-middleware, graceful shutdown
5. Кэш `access_hash` в `telegram.Client`
6. `front_end`: каркас, типы, `lib/group` и `lib/format` с тестами
7. Компоненты и шесть состояний экрана
8. Dockerfile'ы, `nginx.conf`, compose, `.env`
9. README: подъём, логин, dev-режим
