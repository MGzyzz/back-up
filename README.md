## Требования

- Для запуска дашборда: Docker с Docker Compose и Telegram-аккаунт,
  который состоит в канале уведомлений.
- Для Go-команд без Docker: Go 1.27+.
- Для разработки фронтенда без Docker: Node.js 22+ и npm.
- Для публикации отчётов: Google-аккаунт, OAuth-клиент и папка Google Drive.

## Настройки и секреты

Все команды ниже выполняются из корня клона, если явно не указан `cd`.
При первой настройке создайте файлы из шаблонов. Уже заполненные файлы
повторно копировать не нужно — это перезапишет ваши настройки.

```sh
cp back_end/.env.example back_end/.env
cp back_end/configs/config.example.yaml back_end/config.yaml
mkdir -p back_end/data back_end/secrets
chmod 600 back_end/.env back_end/config.yaml
```

- `back_end/.env` — единственный рабочий файл секретов; не хранится в Git.
- `back_end/.env.example` — шаблон без секретов; приложение его не читает.
- `back_end/config.yaml` — параметры канала, расписания, отчётов и API.
- `back_end/data/` — созданные при входе сессия Telegram и токен Google.
- `back_end/secrets/` — OAuth JSON Google, если используются отчёты.

`secrets/` создаётся пустым: сам OAuth JSON в Git не хранится, его кладут
руками по инструкции из раздела про отчёты. Дашборду он не нужен, а вот
`report` без него не обойдётся — и узнает об этом поздно. `.env.example`
уже задаёт `GOOGLE_OAUTH_CLIENT=secrets/client_secret.json`, а проверка
настроек считает достаточным непустое значение и существование файла
не проверяет. Поэтому `report -login` сначала проведёт вход в Telegram
и только потом откажет на Google. Перед входом убедитесь, что файл на месте:
`ls -l "$GOOGLE_OAUTH_CLIENT"`.

Отдельный `env.sh` не нужен. Docker Compose загружает `back_end/.env`
через `env_file`. При локальном запуске Go переменные нужно экспортировать
в оболочку — пример приведён ниже. Значения с пробелами и специальными
символами заключайте в одинарные кавычки.

Получите `api_id` и `api_hash` приложения Telegram на
[my.telegram.org](https://my.telegram.org), затем заполните `.env`:

```sh
TELEGRAM_API_ID=1234567
TELEGRAM_API_HASH='ЗАМЕНИТЬ'
TELEGRAM_PHONE='+77001234567'
# Только для входа, если включена двухфакторная защита:
# TELEGRAM_2FA_PASSWORD='ЗАМЕНИТЬ'

# Используется командой report:
GOOGLE_OAUTH_CLIENT=secrets/client_secret.json
```

Основные поля `config.yaml`:

| Поле | Назначение |
|---|---|
| `telegram.channel_id` | Настоящий ID канала, короткий или в формате `-100…` |
| `telegram.session_path` | Путь к сессии, обычно `./data/session.json` |
| `schedule.timezone` | Часовой пояс границ суток и времени сообщений |
| `schedule.report_at` | Время ежедневного запуска с `report -daemon` |
| `labels` | Значение `LABELS` → отображаемое имя задачи |
| `server.addr` | Адрес API, по умолчанию `:8080` |
| `server.cache_ttl_today` | Кэш сегодняшнего отчёта, по умолчанию `60s` |
| `server.cache_ttl_past` | Кэш прошлых дней, по умолчанию `1h` |
| `google.folder_id` | Папка Google Drive для отчётов |
| `google.token_path` | Путь к пользовательскому OAuth-токену |
| `google.retention_days` | Срок хранения отчётов, в примере 30 дней |

**ID `-1001234567890` в шаблоне — пример.** С ним вход возможен, но получить
отчёт из вашего канала не получится. Замените его до проверки отчёта.
Если ID неизвестен, получите список каналов после входа по инструкции ниже.

Сессия Telegram даёт доступ к аккаунту. Не добавляйте `.env`, конфиг,
сессии и OAuth-файлы в Git; они уже исключены через `.gitignore`.

## Дашборд в Docker

### 1. Собрать образы

```sh
docker compose build
```

Первой сборке нужен интернет для скачивания образов и зависимостей.

**Только Linux.** Перед входом предоставьте пользователю контейнера
(UID 10001) доступ к каталогу сессии и чтение конфига:

```sh
sudo chown -R 10001:10001 back_end/data
sudo chown 10001:10001 back_end/config.yaml
```

Это относится к bind mount: права каталога внутри образа не меняют права
смонтированных файлов хоста.

**На macOS и Windows этот `chown` выполнять не нужно, и он ломает запуск.**
Docker Desktop держит контейнеры в виртуальной машине и читает bind mount от
имени вашего пользователя хоста, а не от UID контейнера. Файл, отданный
UID 10001 с правами `0600`, после chown недоступен уже самому хосту, и вход
падает на `прочитать конфиг: open config.yaml: operation not permitted`.
Оставьте обычные права: владелец — вы, режим `0600` менять не требуется.
Если chown уже выполнен, верните владельца себе:

```sh
sudo chown -R "$(id -un):staff" back_end/data back_end/config.yaml
```

Там же не запускайте `docker compose` под `sudo`: клиент запишет служебные
файлы в `~/.docker` от root, и следующий обычный запуск упадёт на
`~/.docker/buildx/current: permission denied`. Лечится так же — возвратом
владельца: `sudo chown -R "$(id -un):staff" ~/.docker`.

### 2. Войти в Telegram

```sh
docker compose run --rm -it back_end /app/api-server -login
```

Введите код в терминале. Способ доставки выбирает Telegram, программа
показывает его при входе. Пароль 2FA берётся из `TELEGRAM_2FA_PASSWORD`.
Сессия сохраняется в `back_end/data/session.json`; при следующих запусках
используется этот файл. Google для этой команды не требуется.

### 3. Указать ID канала

Если ID уже известен, запишите его в `telegram.channel_id`.
Иначе после входа выполните:

```sh
docker compose run --rm back_end /app/report -channels
```

Команда выводит ID и названия каналов и супергрупп аккаунта, не публикуя отчёт.
В текущей реализации флаг `-channels` есть только у `report`, и эта команда
проверяет наличие настроек Google даже для списка каналов. Для этого шага
достаточно оставить блок `google` из шаблона и непустой `GOOGLE_OAUTH_CLIENT`
из `.env.example`: OAuth JSON и вход в Google при `-channels` не используются.

Замените пример ID в `back_end/config.yaml` числом из нужной строки.

### 4. Запустить и проверить

```sh
docker compose up -d
docker compose ps
curl --fail http://localhost:8080/api/health
curl --fail http://localhost:8080/api/report
```

Откройте [дашборд](http://localhost:8080). `health` отвечает
`{"status":"ok"}`, если HTTP-сервер работает; доступ к Telegram он не проверяет.
Успешный `/api/report` возвращает JSON со списком `jobs`.

По умолчанию интерфейс выбирает сегодня в часовом поясе браузера.
Бэкенд определяет сутки по `schedule.timezone`; для одинаковой даты и времени
используйте соответствующий часовой пояс на компьютере.

После выбора другой даты кнопка называется «Показать», для текущего отчёта —
«Обновить». Запрос уходит по кнопке или Enter. Листание календаря и потеря
фокуса запросов не отправляют. Автоматического опроса нет.

Бэкенд возвращает действующий кэш без обращения к Telegram; рядом со временем
получения появляется «из кэша». После истечения TTL следующий запрос читает
Telegram заново. Перезапуск бэкенда очищает кэш в памяти.

Для отдельного тестового клона, если порт 8080 занят, измените только в нём
публикацию порта в `docker-compose.yml` на `"127.0.0.1:8081:80"`.
Используйте отдельное имя проекта во всех Compose-командах:
`docker compose -p backup-readme-check …`. Адрес проверки станет
`http://localhost:8081`; внутренний порт API остаётся 8080.

### Обслуживание и ошибки

```sh
# Применить изменения config.yaml:
docker compose restart back_end

# Применить изменения .env (restart не перечитывает окружение контейнера):
docker compose up -d --force-recreate back_end

# Пересобрать изменённый код:
docker compose up -d --build

# Посмотреть последние логи:
docker compose logs --tail=50 back_end

# Остановить контейнеры:
docker compose down
```

| Ситуация | Действие |
|---|---|
| `503`, нужен `-login` | Пройти вход в Telegram |
| Канал не найден | Проверить настоящий ID и участие аккаунта в канале; затем перезапустить бэкенд |
| `FLOOD_WAIT` / просьба подождать | Выждать указанный срок, не повторять запросы подряд |
| `400`, неверная или будущая дата | Выбрать существующий день в формате `YYYY-MM-DD` |
| `permission denied` | Проверить права bind mount на конфиг и каталог сессии |
| `operation not permitted` на конфиге или сессии | macOS/Windows: снят chown на UID 10001 — вернуть владельца bind mount себе |
| Пустой `jobs` | За выбранные сутки не найдено разобранных сообщений о бэкапах |

Для повторного входа при уже работающем дашборде сначала остановите бэкенд,
чтобы два процесса не использовали одну сессию одновременно:

```sh
docker compose stop back_end
docker compose run --rm -it back_end /app/api-server -login
docker compose up -d
```

Не запускайте одновременно локальный сборщик отчётов и контейнер API с одним
файлом сессии. Мьютекс API защищает запросы внутри одного процесса.

## Разработка без Docker

Подготовьте `.env` и `config.yaml`, как описано выше. В первом терминале:

```sh
cd back_end
set -a
. ./.env
set +a
# Если сессии ещё нет:
go run ./cmd/api-server -login
go run ./cmd/api-server
```

Во втором терминале, из корня клона:

```sh
cd front_end
npm ci
npm run dev
```

Фронт доступен на [localhost:5173](http://localhost:5173), API — на 8080.
Vite проксирует `/api` на бэкенд, nginx делает это в Docker.
Не запускайте локальный API на 8080 одновременно с Docker-фронтом на этом порту.

## Отчёты Google Sheets

Этот режим дополнительно требует Google Drive API и Google Sheets API,
OAuth-клиент типа Desktop app и доступную пользователю папку Google Drive.
Используется OAuth личного аккаунта со scope
`https://www.googleapis.com/auth/drive.file`.

В [Google Cloud Console](https://console.cloud.google.com) включите оба API,
настройте OAuth consent screen и создайте Desktop OAuth client. Если приложение
в режиме Testing, добавьте свой аккаунт в Test users. Скачанный JSON сохраните
в `back_end/secrets/client_secret.json`, а ID папки укажите в
`google.folder_id`. В `.env` задайте `GOOGLE_OAUTH_CLIENT` с путём к JSON.

Далее команды выполняются из `back_end/`:

```sh
cd back_end
set -a
. ./.env
set +a
go build -o backup-report ./cmd/report
./backup-report -login
```

`report -login` выполняет вход и в Telegram, и в Google. Браузер команда
не открывает: ссылку для Google она печатает в терминал, открыть её нужно
самому. Если приложение в Google Cloud осталось непроверенным, на
предупреждении выберите «Дополнительные настройки» → «Перейти».
Создаются `data/session.json` и `data/google_token.json`.

```sh
# Отчёт за сегодня:
./backup-report

# Отчёт за конкретный прошедший день:
./backup-report -date=2026-09-06

# Публикация отчёта без удаления старых файлов:
./backup-report -date=2026-09-06 -dry-run
```

`-dry-run` **публикует отчёт**; он отключает только отправку старых файлов
в корзину. Отчёт создаётся в заданной папке Drive под именем
`backup-report-YYYY-MM-DD`, с листами «Сводка» и «Детали».

Если файл с таким именем уже существует в папке Drive, публикация пропускается,
существующий файл не обновляется. Очистка старых отчётов всё равно выполняется.
Для повторного формирования сначала переименуйте или уберите прежний файл.
Локальный файл на диске не используется для проверки дубликатов.

Старые отчёты определяются по дате в имени и отправляются в корзину, если
дата строго раньше границы `сегодня − retention_days`. Ошибки очистки
записываются в лог, но не превращают успешную публикацию в ошибку запуска.

| Флаг `report` | Назначение |
|---|---|
| `-config` | Путь к конфигу, по умолчанию `config.yaml` |
| `-login` | Вход в Telegram и Google, затем выход |
| `-channels` | Список каналов аккаунта, затем выход |
| `-date` | День отчёта; по умолчанию сегодня, будущие даты отклоняются |
| `-dry-run` | Не удалять старые отчёты, публикация остаётся включена |
| `-daemon` | Ждать ежедневного времени `schedule.report_at` |

Два сочетания команда отвергает, а не выполняет частично: `-login` вместе
с `-channels` и `-date` вместе с `-daemon`. Молча проигнорированный флаг был бы
хуже отказа — с ним легко решить, что отчёт построен за указанный день.

Пример cron для клона в `/opt/backup-report`:

```cron
0 11 * * * cd /opt/backup-report/back_end && set -a && . ./.env && set +a && ./backup-report
```

Cron использует часовой пояс планировщика. Режим `-daemon` использует
`schedule.timezone`. Выберите один способ ежедневного запуска.

Образ бэкенда содержит оба бинаря, но штатный Compose запускает только API.
Для Google-отчётов нужны дополнительные настройки и OAuth-файлы: каталог
`secrets/` штатным Compose в контейнер не монтируется.

## Как считается статус

Сообщения выбираются по времени доставки в Telegram за сутки в
`schedule.timezone`. Парсер распознаёт `SUCCESS` как успех, `FAILED` и `FIRING` как провал,
а сообщения со статусом `error` — как ошибку выполнения. Сообщения
восстановления пропускаются.

В сводке одна строка соответствует паре `(окружение, LABELS)`. Если хотя бы
одна нода сообщила `SUCCESS`, задача успешна. Это правило рассчитано на кластер,
где остальные ноды могут сообщать, что команда на них не выполнялась.
Бэкап без единого сообщения не появится: справочника ожидаемых запусков нет.
Время и длительность в сводке берутся у успешной ноды; без них выводится прочерк.

## Проверки

Из корня клона:

```sh
(cd back_end && go test ./... && go vet ./...)
(cd front_end && npm ci && TZ=Asia/Almaty npm test && npm run build)
```

Тесты используют подставные данные и не требуют Telegram-сессии или Google.
Для первоначальной установки зависимостей нужен интернет. Часть тестов
форматирования времени предполагает часовой пояс Алматы — он указан в команде.
Актуальное покрытие Go можно получить командой `go test -cover ./...` из
`back_end/`; фиксированные проценты в README не поддерживаются.
