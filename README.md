# backup-report


## Требования

- Go 1.27+
- Telegram-аккаунт, состоящий в канале с уведомлениями
- Google-аккаунт с папкой для отчётов

## Подготовка

### Telegram

1. Открыть https://my.telegram.org → **API development tools**, завести приложение.
   Получить `api_id` и `api_hash` (выдаются один раз на аккаунт).
2. Убедиться, что аккаунт подписан на канал с уведомлениями.
3. ID канала узнать нечем — его покажет сам сервис командой `-channels`
   после входа (см. «Запуск»).

### Google

1. https://console.cloud.google.com → создать проект.
2. **APIs & Services → Library** → включить **Google Drive API** и **Google Sheets API**.
3. **Google Auth Platform → Audience** → добавить свою почту в **Test users**.
4. **Google Auth Platform → Data Access** → добавить scope
   `https://www.googleapis.com/auth/drive.file`.
5. **Google Auth Platform → Clients** → создать клиент типа **Desktop app**,
   скачать JSON.
6. Создать в Drive папку для отчётов, скопировать `folder_id` из URL —
   хвост после `/folders/`.

> Вход сделан через OAuth личного аккаунта, а не через сервисный: у сервисного
> аккаунта нет своего места в Drive, и без Общего диска писать файлы ему некуда.
> Рабочая почта с Общим диском на момент разработки (28.07.2026) отсутствовала.

## Конфигурация

Скопировать `configs/config.example.yaml` в `config.yaml` и заполнить:

```sh
cp configs/config.example.yaml config.yaml
```

| Поле | Что задаёт |
|---|---|
| `telegram.channel_id` | ID канала. Принимается и `1234567890`, и `-1001234567890` |
| `telegram.session_path` | Файл сессии MTProto |
| `schedule.report_at` | Время отчёта; используется только с `-daemon` |
| `schedule.timezone` | Часовой пояс, в котором считаются границы суток |
| `google.folder_id` | Папка Drive для отчётов |
| `google.token_path` | Файл OAuth-токена |
| `google.retention_days` | Сколько дней хранить отчёты |
| `labels` | Карта `LABELS` из сообщения → имя бэкапа в отчёте. Имена должны различать задачи |

Секретов в конфиге нет — они берутся из окружения. Заготовка лежит
в `configs/env.example.sh`:

```sh
export TELEGRAM_API_ID=1234567
export TELEGRAM_API_HASH=...
export TELEGRAM_PHONE=+77001234567
export TELEGRAM_2FA_PASSWORD=...          # только для -login, если включена 2FA
export GOOGLE_OAUTH_CLIENT=/path/to/client_secret.json
```

Файлы `config.yaml`, `data/` и `secrets/` — в `.gitignore`.

**`data/session.json` — это полный доступ к Telegram-аккаунту**, а не отзываемый
токен бота. Права `0600`, на сервер копировать только по ssh.

## Запуск

Шаги 1–5 делаются один раз, при настройке. Дальше сервис запускается одной
командой.

### 1. Собрать

```sh
go build -o backup-report .
```

### 2. Заполнить конфиг и секреты

```sh
cp configs/config.example.yaml config.yaml
cp configs/env.example.sh env.sh && chmod 600 env.sh
```

В `config.yaml` подставить `google.folder_id`, в `env.sh` — значения, полученные
в разделе «Подготовка». `telegram.channel_id` пока оставить как в примере:
настоящий ID узнаётся на шаге 4, а пустым это поле быть не может — без него
сервис не стартует.

Секреты живут в окружении, а не в конфиге, поэтому в каждой новой оболочке:

```sh
source ./env.sh
```

Если чего-то не хватает, сервис перечислит **все** недостающие переменные разом
и завершится с кодом 1 — а не по одной за запуск.

### 3. Войти в Telegram и Google

```sh
./backup-report -login
```

Telegram спросит код и **сам скажет, куда его прислал**:

```
код отправлен: СООБЩЕНИЕМ В САМ TELEGRAM (служебный чат «Telegram»), не по SMS —
  так бывает, когда на номере уже есть активная сессия
код:
```

Способ доставки выбирает Telegram, а не сервис. Если на номере уже есть хоть
одна активная сессия, код почти всегда уходит **внутрь приложения**, в служебный
чат «Telegram», — SMS при этом не придёт вовсе, и ждать её бесполезно.

Если на аккаунте включена двухфакторная защита, пароль берётся из
`TELEGRAM_2FA_PASSWORD`. Google откроет браузер.

Команда требует терминала и выполняется руками: под cron спросить код некому.
Результат — `data/session.json` и `data/google_token.json`; пока они
действительны, вход больше не нужен.

### 4. Узнать ID канала

```sh
./backup-report -channels
```

```
CHANNEL_ID     НАЗВАНИЕ
1234567890     backup notifications
```

Полученное число — в `telegram.channel_id` файла `config.yaml`.

### 5. Проверить

```sh
./backup-report -date=2026-08-20 -dry-run
```

Отчёт строится как обычно, но старые файлы только перечисляются в логе, а не
отправляются в корзину. Полезно на первом запуске, пока не видно, что попадёт
под `retention_days`.

### 6. Обычный запуск

```sh
./backup-report
```

Отчёт за сегодня, с чисткой старых. Ненулевой код возврата означает, что отчёт
не построен, — по нему планировщик и узнаёт о сбое. В случае если на диске уже хранится отчет, то второй отчет за тот же не создаться. Нужно удалить старый отчет того дня

В cron:

```
0 11 * * *  cd /opt/backup-report && . ./env.sh && ./backup-report
```

`. ./env.sh` здесь обязателен. Cron запускает задачу с почти пустым окружением:
без этой части команды сервис не найдёт ни одной переменной и упадёт на проверке
конфига.

### Флаги

| Флаг | Что делает |
|---|---|
| `-config` | Путь к конфигу (по умолчанию `config.yaml`) |
| `-login` | Интерактивный вход в Telegram и Google, затем выход |
| `-date=2026-08-20` | Отчёт за указанный день вместо сегодняшнего |
| `-dry-run` | Старые отчёты не удалять, только показать в логе; отчёт публикуется как обычно |
| `-daemon` | Не выходить, а ждать `schedule.report_at` |
| `-channels` | Показать каналы аккаунта с их ID и выйти |

`-date` закрывает три сценария: догон после простоя, перегенерацию отчёта после
починки парсера и ручную проверку. Дату из будущего сервис не примет: сообщений
за ненаступивший день быть не может, а пустой отчёт занял бы имя и заблокировал
настоящий, когда день придёт.

`-daemon` нужен там, где планировщика нет вовсе: процесс не завершается, а спит
до `schedule.report_at`. При наличии cron проще запускать без флага — одним
проходом.

## Устройство

```
main.go                 флаги, интерактивные режимы, сборка зависимостей, коды возврата
internal/app/           последовательность шагов: прочитать, разобрать, опубликовать, прибрать
internal/config/        конфиг, секреты из окружения, валидация
internal/dates/         операции над сутками, общие для транспорта и отчёта
internal/parser/        разбор текста сообщения в структуру Backup
internal/report/        свёртка бэкапов в задачи, строки обеих таблиц, правило хранения
internal/telegram/      MTProto: вход, поиск канала, чтение истории за сутки
internal/gsheets/       OAuth, создание файла, заливка, листинг, чистка
```
## Тесты

```sh
go test ./...
```

Проходят без интернета, без сессии Telegram и без токенов Google.

```
internal/dates    100.0%
internal/parser    97.7%
internal/report    95.1%
internal/config    90.2%
internal/app       81.4%
internal/gsheets   33.9%
internal/telegram  20.9%
main               13.0%
```

Низкие два числа — осознанный размен. MTProto нельзя
подделать через `httptest`: это бинарный протокол поверх TCP со своей
криптографией, а Google API требует живых учётных данных. Поэтому сетевые слои
сделаны тонкими и без логики, а всё, что можно посчитать неправильно, вынесено
в чистые функции и в `internal/app`: разбор сообщения, границы суток,
нормализация ID канала, сборка строк, правило хранения, защита от формул
и весь порядок шагов. Они покрыты почти полностью.
